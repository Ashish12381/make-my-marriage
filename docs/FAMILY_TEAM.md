# Family & Team — 30 October 2026

This milestone implements planning-team membership and invitations. Guest/family RSVP invitations are separate. Event-specific responsibilities await the events feature.

## Implemented journey

Open a wedding overview, then **Family & Team**. Wedding Admins see Members and Invitations, can invite an Admin or Organizer, change member access, remove members, and revoke pending unexpired invitations. Organizers see a read-only member list and their own access summary; other members' email/permission details and the Invitations tab are omitted. Full membership management is Admin-only.

The implementation follows the existing Stitch Family & Team and Invite Member screens in project `9065562061050388454` (screen IDs `193ab4aa62684734bb7556ccb87ae23d` and `6bff39ba374d4a7da9c387a84965d228`). It uses one shared responsive native dialog with a visible email input, nine unchecked Organizer permissions, full-access Admin explanation, validation, busy/error states, cancellation and confirmation before removal. The desktop dialog becomes a full-screen sheet on mobile. Preview controls, budgets, payment processing and fabricated metrics are not included.

Invitation links open `/invite/member/:token`. Preview shows the wedding title, offered role/permissions, expiry, invited email and whether that invited address has an account. The recipient details are returned only after validating the pending, unexpired invitation token; there is no arbitrary email/account lookup endpoint. Acceptance requires a real session, the valid token, and an account whose normalized email matches the invited email. A different account receives `403 INVITE_EMAIL_MISMATCH` without consuming the invitation; Switch account remains available. This is the user's approved 2 November 2026 revision to the original token-only rule. Signup still requires a separate login. Auth continuation accepts only a validated membership-invitation path; arbitrary redirect URLs are rejected. Decline requires the valid token and explicit confirmation. No email verification is required, and matching an email alone grants no access. The UI/email explain which account to use and that the link is private.

To repeat a test, revoke a pending invitation in Invitations, or remove an active member through Members → Manage access → Remove member. Removal revokes wedding access while retaining the app account and history; a new invitation can reactivate the same membership row. Accepted history alone does not block another invitation. The last active Wedding Admin cannot be removed. The Invitations tab explains where each action belongs. No historical accepted invitation is reset or deleted for testing.

Successful acceptance adds/reactivates the unique user/wedding membership. Acceptance by an already-active member returns `409 ALREADY_A_MEMBER` and leaves the invitation pending. The invitation page offers **Switch account**, which signs out and returns through login to the same invitation. Existing members' roles are not changed through acceptance. Consumed invitations return `409 INVITE_ALREADY_USED`; revoked/expired/invalid tokens are unavailable. The member list, invite history and dialogs revalidate on session hints/focus, retain draft entries on transient refresh failures, and clear private data on rejected access.

## Backend and persistence

The routes specified in API Design section 5 are mounted: member listing; invite creation/history/revocation; minimal public token preview; authenticated acceptance; token-authorized decline; Admin-only role/permission update and member revocation. Boundaries use strict Zod schemas, authenticated sessions where required, private no-store responses, exact Origin and CSRF checks for writes. Public invite responses use no-referrer, and invite/auth continuation pages set a no-referrer policy and noindex metadata.

`memberships` owns `wedding_memberships` and `membership_invites`. `email` owns `email_deliveries`; its complete canonical schema is implemented. No additional collections, JWTs, browser token storage, message queues or workers were introduced. Auth profile lookup, wedding validation/serialization and audit writes use public module interfaces.

Every membership mutation first writes the active wedding document's Mongoose version (`__v`) through the weddings public interface inside a transaction. This serializes invite creation/acceptance/revocation and member changes, and forces conflicting transactions to retry and recheck actor permissions and Admin count. Removal or demotion of the last active Admin returns `409 LAST_WEDDING_ADMIN`, including concurrent requests. Member changes retain history as `REVOKED` instead of deleting rows. Important mutations record actor IDs and action/resource references in audit logs without bearer tokens.

Invites contain random 256-bit opaque tokens; only SHA-256 hashes are persisted. Expiry is seven days. Creation rejects existing active members and duplicate pending unexpired invites within the wedding. A conservative operational ceiling of 20 invite creations per wedding per rolling hour limits accidental/provider abuse; it is not a wedding-count or guest limit. The UI displays expiry-derived EXPIRED status without deleting history.

The canonical database includes a `members` permission flag, but the approved API/design reserves membership administration for Admins. Organizer input exposes only the nine planning areas and never accepts `members`; its stored value remains false. The public `requireWeddingFeature` capability enforces individual areas for future modules. Actual events/tasks/finance endpoints must call that capability as they are implemented; configuring a permission does not make a deferred module operational.

## Resend delivery

One bounded email request occurs after a successful invitation transaction. Provider calls never execute inside retried transactions. The integration uses Resend's documented POST `/emails` API with an idempotency key derived from the invitation ID. `email_deliveries` records attempts, provider message IDs and sanitized outcomes; the raw invite URL/token is never stored in delivery records or returned to the inviting browser.

- SENT means Resend accepted the send request, not inbox delivery.
- FAILED covers missing configuration or explicit provider rejection.
- UNKNOWN covers timeouts, network errors, server errors or unconfirmed outcomes. No blind automatic retry occurs.
- A created invitation remains visible if sending fails. The UI tells the Admin to check Invitations rather than recreate it blindly. Raw links are not exposed as a fallback, and resend is outside this slice. After correcting configuration, revoke an unusable pending invitation and create a new one.

`RESEND_API_KEY` and `RESEND_FROM_EMAIL` are configured locally. The user authorized one real test invitation from the retained QA wedding to the configured sender address. Creation returned 201, but Resend rejected the send because the sender domain is not verified (`SENDER_DOMAIN_NOT_VERIFIED`). Its pending invitation ID is `6ae4306b3acc55ea465821d1`; the delivery record is FAILED. It was retained as authorized, without an automatic retry. Configure a sender on a verified domain before further delivery tests. Inbox delivery remains unverified. Provider references: [Resend Send Email API](https://resend.com/docs/api-reference/emails/send-email), [Verified Domains](https://resend.com/docs/dashboard/domains/introduction).

Admin invitation history displays persisted email status separately from invitation state. Pending does not imply sent; SENT means accepted for sending, FAILED means not sent, and UNKNOWN means unconfirmed. No raw provider error details, credentials or private links are exposed.
